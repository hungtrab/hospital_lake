## Slide 2 — HospitalLake connects data to analytics

A hospital produces many kinds of records, including admissions, laboratory results, medications, and bed assignments.

These records need to be connected and checked before we can use them for analysis.

HospitalLake brings them into a shared data platform. It preserves the original records, creates clean tables, and calculates useful metrics.

For this milestone, we have built a runnable local batch pipeline using synthetic hospital data.

Let me first introduce the dataset.

## Slide 3 — Six entities model hospital activity

Our dataset contains six groups: patients, encounters, lab results, medication orders, vital measurements, and bed events.

An encounter means one hospital visit or admission. One patient can have several encounters, and each encounter can have many measurements or laboratory results.

We connect these records using patient IDs and encounter IDs.

Our default dataset contains one thousand patients and three thousand ninety-four encounter rows.

The data is generated by our own program. With the same seed and settings, we can reproduce the same dataset.

Each file contains a table for one type of hospital record.

Let me show the structure of one file and an actual example.

## Slide 4 — Parquet stores typed tables

Parquet is a file format for storing tables with defined column types. We can display the contents as rows and columns, similar to a spreadsheet.

Here is the structure of the encounters file. It has seven columns, and each row describes one visit or admission.

The encounter ID identifies the visit. The patient ID identifies the patient and connects this row to the patients table.

The encounter type, department, and status are stored as text. Admission time and discharge time are stored as timestamps in UTC.

The discharge time can be empty, or null, if the patient has not been discharged yet.

## Slide 5 — Example: one actual encounter record

This is the first record from our generated encounters file. We have displayed one row vertically so that the fields are easier to read.

It describes an inpatient visit for the patient identified by the patient ID on the slide.

The patient was admitted on December eighth, twenty twenty-five, and discharged on December tenth. The exact times are shown in UTC.

The department is written as SURG in the raw file. During cleaning, we standardize this value to SURGERY. The status is discharged.

This example shows both the structure of our input and a value that the pipeline needs to standardize. The record is synthetic, even though it comes from an actual generated file.

Now, let us look at how these files move through the system.

## Slide 6 — The batch pipeline feeds historical analytics

This milestone focuses on the batch path, which handles historical files.

Spark reads the Parquet files and creates the Bronze, Silver, and Gold tables. Trino allows us to query the results using SQL.

MinIO stores the files, while Iceberg organizes them into tables. Spark performs the data processing, and Trino answers analytical questions.

Our target design also includes a streaming path, but it is still in progress and is not ready for demonstration.

ClickHouse and Grafana are planned for realtime queries and dashboards after the streaming path is ready.

Next, I will explain the three data layers in the batch path.

## Slide 7 — Batch keeps raw data and isolates errors

We organize the batch data into three layers.

Bronze preserves the original rows and adds ingestion information.

Silver standardizes values, merges identical copies, and checks whether records are valid. Invalid records are kept separately with a reason.

Gold contains the aggregated tables used for analysis.

For example, our encounter input has three thousand ninety-four rows. After processing, we have three thousand fifty-eight valid rows.

Thirty-one duplicate copies are merged, and five invalid rows are quarantined. This helps us explain exactly why the row count changes.

After preparing the data, we can use it to answer analytical questions.
